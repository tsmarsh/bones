Why Plain Text Works for Authors

Developer tools and author tools share more in common than you might think

What is Plain Text?

Plain text is simply text without proprietary formatting - files you can open in any text editor, on any computer, decades from now. When you write in Markdown (a simple plain text format), you're creating files that are:

  • Future-proof - No vendor lock-in, no obsolete file formats
  • Version-controllable - Track every change with Git
  • Searchable - Find anything instantly across your entire manuscript
  • Portable - Work on any device, any operating system
  • Automatable - Use scripts and tools to transform your work

Compare this to proprietary formats like .docx or .pages that require specific software, can become corrupted, and may not open in future versions of the software.

The Plain Text Difference

Proprietary Format: Your novel exists as a binary file that only Microsoft Word can properly read. If Word changes its format (as it has many times), you might lose formatting or even content.

Plain Text: Your novel exists as readable text files that any editor can open. The same file that works today will work in 50 years.

Developers and Authors: The Same Problems

Software developers and fiction authors face remarkably similar challenges. Both are creating complex, interconnected works that evolve over time. Both need to track changes, collaborate with others, and manage multiple versions. Here's how the problems align:

🔄 Version Control

Developer: "I need to track every change to my code and be able to roll back if something breaks."

Author: "I need to track every revision and be able to return to earlier drafts if my rewrites don't work."

Solution: Git version control

🔍 Search & Find

Developer: "I need to find every place I used this function name across hundreds of files."

Author: "I need to find every mention of this character across my entire manuscript."

Solution: grep, ripgrep, or text search tools

👥 Collaboration

Developer: "Multiple people need to work on this project without overwriting each other's changes."

Author: "I need my editor and beta readers to suggest changes without destroying my original."

Solution: Git branches and merging

🧩 Modularity

Developer: "I need to organize my code into logical files and folders."

Author: "I need to organize my manuscript into chapters, sections, and scenes."

Solution: File system organization with build tools

🤖 Automation

Developer: "I need to automatically test, format, and package my code."

Author: "I need to automatically format, spell-check, and generate PDFs from my manuscript."

Solution: Build systems (make, scripts)

📊 Consistency

Developer: "I need to ensure my code follows consistent style and naming conventions."

Author: "I need to ensure character names, terminology, and world-building details stay consistent."

Solution: Linters, validators, AI tools

Because the problems are so similar, the solutions transfer beautifully. Tools built for developers - Git, text editors, build systems, search tools - work just as well for authors once you understand the parallels.

Advantages of a Plain Text Workflow

💪 Ownership & Control

You own your manuscript completely. No subscriptions, no cloud services required, no wondering if your work is being used to train AI models. Your files, your computer, your control.

🚀 Speed & Performance

Plain text editors are lightning fast. No waiting for Word to load, no lag while typing, no crashes with large documents. Open a 200,000-word manuscript instantly.

🔧 Powerful Tools

Access to decades of powerful developer tools: advanced search, regex, scripting, automation, version control, diffing, merging, and more.

🎯 Focus on Content

Markdown separates content from formatting. Write first, format later. No fiddling with fonts and margins while drafting - just pure writing.

🔄 Format Once, Output Anywhere

From a single Markdown manuscript, generate PDFs, ePubs, HTML, or any other format. Change your mind about formatting? Regenerate in seconds.

📜 Future-Proof

Plain text files from the 1970s are still perfectly readable today. Can you say the same about your Word Perfect files from 1995?

🧪 Experimentation

With Git, experimenting is risk-free. Try radical rewrites, kill characters, change settings - all without fear of losing your original work.

🤖 AI Integration

Plain text is perfect for AI tools. Feed your manuscript to language models for editing, suggestions, or analysis without format conversion headaches.

💼 Professional Output

LaTeX (which Bones uses) produces typography that rivals professional publishers. Better kerning, ligatures, and spacing than Word could dream of.

A Day in the Life: Plain Text vs. Word Processor

Traditional Word Processor Workflow

  • Open Microsoft Word (wait for it to load)
  • Navigate through menus to find your file
  • Wait for large document to load
  • Make changes, fighting with formatting issues
  • Save manually (hope it doesn't corrupt)
  • Email a copy to yourself "just in case"
  • Save another copy with today's date in filename: novel_final_REALLY_FINAL_2024_v3.docx
  • Try to remember which version has the changes you want
  • Spend time copying and pasting between versions
  • Pray your formatting survives when you send to beta readers

Plain Text Workflow with Bones

  • Open your text editor (instantly)
  • Edit any chapter file (opens immediately, no lag)
  • Save automatically (most editors do this)
  • Commit changes with a meaningful message: git commit -m "Revised Chapter 5 ending"
  • Generate a fresh PDF: bones pdf
  • Want to try something different? git checkout -b experimental-ending
  • Don't like it? git checkout main - back to safety
  • Need to find everywhere you mentioned a character? grep -r "Dracula" src/
  • Send to beta readers knowing they can't mess up your source files
  • Every version in history is one command away
💡 The Learning Curve is Worth It

Yes, there's a learning curve. Git, Markdown, and command-line tools aren't as immediately intuitive as clicking around in Word. But once learned, these skills are transferable, powerful, and will serve you for decades. Word's interface will change in the next version; Git and Markdown will work the same way in 2050.

What About Formatting?

This is the biggest objection authors have to plain text: "But I need formatting!"

The truth is, you need formatting in your output, not while you're writing. Markdown gives you everything you need while drafting:

# Chapter Title

This is a paragraph with *italics* and **bold**.

> This is a quote or epigraph.

- Lists
- Are
- Easy

## Scene breaks work like this

And that's 95% of what fiction needs.

When you're ready to publish, Bones uses LaTeX to generate professional typesetting that surpasses anything Word can produce. Proper kerning, ligatures, widow/orphan control, professional margins - all automatically.

Meanwhile, while drafting, you're not distracted by fonts, sizes, spacing, or margins. You're just writing.

Getting Started is Easier Than You Think

You don't need to master everything at once. Start simple:

  1. Write in Markdown - It's just text with a few simple symbols
  2. Save with Git - git add . and git commit -m "today's work"
  3. Generate PDFs - bones pdf

That's it. You're now using a professional plain text workflow. Everything else - branches, advanced Git features, automation, scripting - you can learn as you need it.

🎯 Start Small

Don't try to move your entire 90,000-word novel to Markdown on day one. Start with a short story or a single chapter. Get comfortable with the workflow. Then expand.
